# formal：两阶段提交（2PC）协调库

供分布式事务协调路径调用的 Go 两阶段提交实现，基于顺序预写日志（WAL）
保证崩溃可恢复，遵循预设中止推定（presumed abort）。

## 协议与日志顺序

每个事务严格按三个阶段产生顺序记录，决策记录落盘之前不会发出任何决议指令：

1. 准备阶段：协调者写 `prepare`，向全部参与者收集赞成票；
2. 决策阶段：全票赞成才写 `commit`，否则写 `abort`；
3. 应答阶段：记录每个参与者的 `commit-ack` / `abort-ack`，最后写
   `end-commit` / `end-abort` 收尾。

## 关键正确性规则

- 决策点未被日志覆盖时不得应答：参与者在准备后、决议前处于存疑状态，
  只能通过 `Resolve` 向协调者查询；协调者无决策记录时查询返回 unknown。
- 预设中止推定：协调者重放发现事务只有准备记录时补写中止决策；
  参与者对从未准备的事务直接确认中止，存疑解析在重试预算耗尽后本地中止。
- 重复决议幂等：参与者重复收到 prepare/commit/abort 返回同一结果，
  协调者对同一事务的重复、并发 `Run` 调用返回唯一决议，决策记录只写一次。
- 部分应答确定性收尾：提交决议持久化后，应答未齐只能返回带
  `ErrPendingAcks` 的提交结果并等待恢复/存疑解析，绝不回退为中止；
  中止路径在预设中止推定下可直接写收尾记录。
- 无混合提交：`AssertLogInvariants` 校验日志中不存在 commit/abort 双决策、
  无决策应答或收尾与决策不一致等非法历史。

## 崩溃恢复与重放

- `FileWAL` 每条记录追加后 `fsync`，帧带 CRC32；崩溃造成的截断尾部
  在重放时被物理截断，完整帧不受影响。
- 协调者与参与者构造时都会重放各自 WAL 重建内存状态。
- `ReplayOutcome` 是不依赖任何进程内存的独立推导函数，测试用它交叉核对
  协调者日志、参与者日志与运行时最终状态逐事务一致。

## 验证

```bash
go test -race -count=1 ./...
go test -cover ./...
```

测试通过崩溃点枚举（协调者 7 个日志点 + 参与者 prepare/commit 后宕机）、
超时/重试交错注入、多事务跨重启重放，核对每个事务最终状态唯一、
与独立重放一致，且不出现混合提交。
